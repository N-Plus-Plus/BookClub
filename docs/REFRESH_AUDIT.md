# Refresh audit

Audited 5 October 2026 against current `origin/main`, commit `af95fdb95628f4c2a5e6af64afbabdcdf50e6f50` (local HEAD matches). Existing uncommitted header/navigation/style work was preserved and excluded from the baseline; its diff does not change refresh behaviour. Read AGENTS.md and STYLE.md in full, and consulted ARCHITECTURE, DATA, CONTRACTS and INTEGRATIONS. This is a source-only audit: no application code edits, tests, typecheck, build, prod:check, browser automation or production access.

**Counts:** 16 distinct control placements: **1 removal**, **0 automatic/screen-entry replacements**, **9 error-recovery controls**, **6 maintenance controls**. Repeated film/member instances count once per placement, as do dynamic label variants. The developer initiation and confirmation buttons are counted separately; they implement one maintenance operation. The shared Failure component counts separately at its two consumers. All listed controls use Lucide `RefreshCw`; none has a separate mobile/desktop refresh implementation.

Recommendations use exactly these outcomes: **1 REMOVE - ALREADY AUTOMATIC**, **2 REMOVE - ALLOW STALE**, **3 REPLACE WITH AUTOMATIC LOCAL REFRESH**, **4 REPLACE WITH SCREEN-ENTRY REFRESH**, **5 KEEP ONLY AS ERROR RECOVERY**, **6 KEEP AS EXPLICIT MAINTENANCE ACTION**.

## Current refresh architecture

### Global catalogue and load()

`App.load()` starts a generation-guarded request, sets refreshing and clears the shared error. It GETs `/health`; hosted authentication then requires a stored session and `/auth/me`, with missing-avatar gating before catalogue access. Development bypass also reads `/auth/me` and ordinary local login gates missing identity/avatar. It then reads `/catalog` and `/rotation` concurrently, replacing both only when the generation is current and both requests succeed. Failures preserve an existing catalogue/rotation and populate the shared error (401 is handled by auth reset). Finally clears loading/refreshing. Its caught failures do not reject the returned promise, so callers awaiting load() cannot infer success merely from completion.

`/catalog` contains stored members, movies, active History sessions and cycles, including stored provider observations and derived ranking. It excludes private Builder/auth records. Worker GET catalogue/detail paths read D1 and derive presentation; they do not invoke rating or metadata providers. `frontend/api.ts` is the ordinary browser API boundary, with authentication, timeouts and 401 handling; it has no automatic revalidation/retry cache.

Home, History, Classics, Seen It? and Metrics render from the global catalogue. Metrics derives calculations client-side, not from a separate metrics endpoint. Event editing seeds its form from catalogue sessions and uses catalogue members/cycles plus global rotation. Builder uses catalogue movies/members/cycles and rotation alongside separately fetched owner-only sets. Detail uses global members but separately fetched MovieDetail. **Global load() does not refresh an already mounted detail's local movie or Builder's local sets/form.** Likewise, its refresh button is not a universal reload of everything visible.

### Automatic updates after app actions

| Action / owner | Existing state update |
| --- | --- |
| App mount; successful Google/local sign-in; avatar claim | Calls global load(). Avatar claim also immediately sets returned viewer. |
| Home rotation correction | PUT rotation then onUpdated → load(); does not require the page-heading button. |
| History Delete | DELETE session then onChanged → load(). |
| Event create/edit | Returned session patches catalogue sessions immediately, then load() refreshes all stored changes, notice is set and navigation goes to History. Full reload covers cycles/rotation and Classics-completion Seen changes. |
| Builder save / Review publication / delete | Save patches editing with returned BuilderSet and GETs `/builders`; Review publication saves before opening review. Delete GETs sets after success. These use Builder's local load(), not App.load(). |
| Builder publication | POST publish then onPublished → global load() and History navigation; server publication removes private set and may change rotation/Seen. |
| Seen answer, Undo, recent-answer correction | PUT Seen returns MovieDetail; App.answer → applyMovie patches catalogue movies and matching movies nested in sessions. Queue, rankings and Metrics recalculate from state. Detail answers also set local movie. |
| Detail Classics membership / score capture / saved-data reconciliation | update() sets local movie and onMovie → applyMovie; no full catalogue refetch. |
| Classics single/bulk score capture | Patches each returned movie through onMovie → applyMovie; groups/ranking recalculate. |
| FilmPicker manual creation / TMDB import | Returned movie is applied globally and added to editor selection. Selecting an already saved search result only adds it to selection. |
| Metrics metadata maintenance | Response counts/results patch local progress per batch; onUpdated → global load() runs after completion, stop or failure, even if navigation unmounted Metrics. |
| Developer identity selector / successful local replacement | onChanged → global load(); identity selection is an identity action with automatic reread, not an extra manual-refresh control. |

These are mostly **confirmed-response state patches**, not speculative optimistic writes. Event save patches before its subsequent global refetch, but only after the server confirms the save. Seen/membership/score failures preserve last confirmed data. Logout revokes the session and resets private state on success; it does not refresh the catalogue.

### Entry, re-entry and deliberate staleness

- Hash changes only set page, scroll to top and focus the heading. They do not call App.load(). Home/History/Classics/Seen/Metrics re-entry continues using the existing catalogue; selecting an already active route also causes no fresh read. Full document reload/remount reruns initial load().
- Builder mounts and reads `/builders` for the viewer, also rerunning when viewer ID changes. Leaving the screen unmounts it, so returning reads sets again. Open set and All sets use already loaded sets; opening uses catalogue film objects. There is no Builder Retry/Refresh button. A global refresh does not resolve a stale private-set revision; re-entry rereads sets.
- Detail is keyed by movie route; mount/re-entry/different movie GETs `/movies/:id`. Same mounted route does not re-fetch when the global catalogue changes. Initial detail GET does not call onMovie, so seeing fresh detail does not itself refresh other catalogue-backed screens. Saved-data reconciliation and successful detail writes do patch both.
- History Audit reads `/sessions/:id/audit` on first opening; successful loaded evidence is reused for subsequent disclosure toggles during that mount. If first loading fails, reopening retries because audit remains unset. This is lazy evidence access/error recovery, not a manual freshness control; keep cached evidence. History re-entry remounts those records.
- Event re-entry remounts the form from the existing global catalogue, not a new session GET. Already mounted form state is not re-seeded by global refresh. FilmPicker Search explicitly queries saved matches plus TMDB for a user-entered query; it is a search task, not a freshness control. Search results stay until another submitted search or remount.
- Avatar availability GET occurs once per chooser mount. Claims do not re-fetch available choices on collision; error is shown and existing choices remain. There is no Refresh choices button. STYLE expressly specifies once-per-interaction availability. No automatic alternative is required by this audit.
- Other clients' writes are not pushed into the current app. Stored provider scores/metadata intentionally remain snapshots until explicit maintenance; a page reload only reads those stored observations. Missing artwork falls back without provider repair.

### Background activity and search coverage

No normal catalogue/detail polling, websocket, service worker, focus-triggered or visibility-triggered refresh exists. Hash listeners perform navigation only. RequestAnimationFrame calls manage focus; the GIS timeout handles script failure. The exceptions to “no polling” are **explicit developer replacement status polling** (one-second GETs only while that operation runs) and the **user-started metadata batch loop**, which performs bounded provider mutations with progress and stop guards rather than passive freshness polling.

Inspected all frontend screen/components, entry/API code and relevant Worker handlers/services. Searched refresh/reload/retry/update labels, RefreshCw and equivalent reload mechanisms, load/refetch/onUpdated/onChanged names, post-write reads, effects and browser events. No additional Refresh choices, Refresh metadata, Refresh catalogue, refresh card/header icons, hidden routine refreshes, or mobile-specific duplicate mechanisms exist on this baseline. “Updated” answer timestamps, “Updating membership…”, provider status copy, filters, route links, History Audit, FilmPicker Search and Stop after this batch are not additional refresh controls.

Documentation observations: DATA, CONTRACTS and INTEGRATIONS correctly distinguish stored reads from explicit maintenance. INTEGRATIONS describes a “six-month metadata cache policy” while the implemented eligibility threshold is 150 days (also documented in DATA and the same integration section); this wording needs alignment in a separately authorised documentation cleanup. STYLE's local retry requirement supports retaining error recovery; it does not require routine freshness buttons. No authoritative files were changed in this audit.

## Recommended cleanup groups

1. **Global/page chrome:** remove the single routine heading refresh Action. Keep load() and its existing automatic callers. Allow shared catalogue state to remain stale for changes made elsewhere until full reload; do not imply current hash re-entry refreshes it. No new polling or screen-entry mechanism is justified by these controls.
2. **Screen-specific stored reads:** preserve Builder/detail mount reads, History lazy audit caching and confirmed-response movie/session patches. There are no routine screen-specific stored-state refresh buttons to replace. Do not make global load() masquerade as refresh of local editor/detail state.
3. **Error-only recovery:** retain all nine conditional recovery placements, including Seen/membership write retries and ambiguous score-result reads. When implementing cleanup, keep their actual error gating and distinguish shared App error causes so connection/load retries do not promise to repeat unrelated operations.
4. **Provider/admin/developer maintenance:** preserve all six controls and automatic result application. Keep explicit disclosures, existing role boundaries, provider outcome feedback, bounded batches and destructive local replacement confirmation. Removing the global icon should not remove provider capture or trigger it automatically.

## No-change controls

- Classics **Enrich up to 10 films**: explicit MDBList/OMDb score snapshots; admin UI, member-authorised API.
- Classics candidate **Refresh scores**: single-film provider capture.
- Film detail **Refresh scores**: same capture with detail and global response patching.
- Metrics **Fill missing metadata** and associated **Stop after this batch**: intentional TMDB maintenance and run control, not routine stored-data reload.
- Developer **Refresh Dev DB from Production** and **Confirm local replacement**: two-step guarded production read/export and destructive local replacement, followed by automatic app reread. Neither was executed.

All other listed retries remain strictly error recovery. No code changes are included or proposed as already implemented.
