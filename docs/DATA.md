## Unified Admin maintenance coverage and progress

`shared/maintenance-contract.ts` declares the eight operation identities, provider capabilities, population, field names/types, optional-value meaning, response sources, persistence destinations and Admin inventory wording. Every declared field must have conclusive provider evidence for a film operation to be complete; optional means its value can legitimately be unavailable, not that its check can be omitted. TMDB response titles and validated collection roster identity/name/members are mandatory. Watch Order still requires its original six dimensions; unified Admin maintains all nine definitions in `rating-dimensions.ts`.

| Operation | Fields / families | Population |
| --- | --- | --- |
| Scores (9) | IMDb, Letterboxd, Metacritic critic/user, RT audience/critic, TMDB, Trakt, Roger Ebert | Distinct Classics and active-History films; MDBList supports all nine, OMDb IMDb/MC critic/RT critic, TMDB its own rating |
| OMDb metadata (5) | Provider title, year, runtime, director, genres | Catalogue with valid IMDb identity |
| TMDB metadata/artwork (9) | Provider title, original title, release date/year, runtime, overview, director, genres, poster, backdrop | Catalogue with valid TMDB identity |

| MDBList enrichment (4) | Provider title, runtime, keywords, safe external identity claims | Identified catalogue, IMDb preferred / TMDB fallback |
| TMDB collections (2) | Collection ID/name, or confirmed absence | Catalogue with valid TMDB identity |

Once film work is successfully checked, skipped or deferred, aggregate planning uses fresh committed eligibility and proceeds to rosters. Unknown membership from failed checks remains an issue. Explicit Retry failed can discover newly eligible rosters as a controlled extension; the original boundary and already successful rosters remain unchanged.

Old origin-local film v1, aggregate v2 and roster v1 checkpoints remain unchanged. All eighteen Admin cards use the shared field inventory and the same durable job model for their operation and intent. Collection counts remain separate work units from film/provider counts.

Guarded local identity tools register the new movie relationship so archival and compatible-field retention continue to work; latest checks are retained per field. Snapshot copying permits this additive table to be absent from older exports. No identity repair or production backfill is part of deployment.

## Builder draft persistence

Builder uses one in-memory serial/coalescing queue per edited private draft. New set alone does not write; film additions/removals/moves (including inspection-confirmed additions) or changed title/note blur enqueue the latest snapshot. Typing stays local; another persist-worthy action may include current text. Each response advances ID/revision without replacing newer fields, and further queued changes use that revision. Successful saves patch local sets directly; no per-save list reload occurs. Queued new drafts remain available through All sets. Failures retain dirty state and stop automatic retries until another edit or explicit Save set. Save set flushes and returns to the list; The Builder UI enables Use set only for the effective active member’s current human turn (including swaps), with a nonempty lineup. Use set flushes before confirmation and publication and publishes the latest saved revision. Draft/queue state is transient, with no browser storage. Unblurred focused text is the ordinary loss window; failed or pending writes remain unconfirmed until persistence succeeds.

To distinguish Stream-service zeroes from separate rental/purchase services, inspect narrowly scoped cached offers. Raw names/IDs precede display aliases; Prime and Amazon purchasing services remain distinct. This diagnostic matches the catalogue's AU access projection and active-History population, without provider calls or writes:

```sql
SELECT o.service_id, o.name, o.access_type, COUNT(DISTINCT o.movie_id) AS films,
       MIN(o.fetched_at) AS oldest_capture, MAX(o.fetched_at) AS newest_capture
FROM movie_provider_watch_offers o
WHERE o.country = 'AU' AND o.access_type IN ('subscription','free','ads','rent','buy')
  AND (lower(o.name) LIKE '%amazon%' OR lower(o.name) LIKE '%prime%'
       OR lower(o.name) IN ('stan','netflix'))

              WHERE sm.movie_id = o.movie_id AND s.deleted_at IS NULL)
GROUP BY o.service_id, o.name, o.access_type
ORDER BY o.service_id, o.name, o.access_type;
```

## Backup, recovery and local snapshots

`corepack pnpm db:refresh-from-prod` is an explicit one-way current-production read/export and local replacement, not archive replay or production mutation. It needs Node 24+, pnpm execution context and Cloudflare operator login or process-only credentials with D1 read/export rights. CLI requires stopped local API; the confirmed development panel supervises API stop/restart. On Windows, Vite file watchers can hold the local D1 directory open and block replacement with EPERM; stop both the UI and API and use the CLI refresh in that case, then restart them. No arbitrary DB target or remote write option is accepted.

The code verifies the exact configured production name/UUID, exports SQL to ignored temporary storage, restores it offline and stages current local migrations. Source application tables must match, except the precisely enumerated ten additive 0016 provider-cache tables and two additive 0020 coverage/failure tables plus three additive 0021 collections/awards/failure tables and the additive 0022 collection roster table and 0023 field-check table plus the four additive 0024 job tables and two additive 0025 planning tables may be absent from an older source and remain empty in the fresh destination; the three reviewed production identity maintenance tables are also supported and preserved locally. Unknown source tables or columns fail closed. The explicitly reviewed pre-0010 source columns `sessions.title`, `sessions.notes` and `sessions.swap_note` are omitted when absent from the destination, supporting a 0009 snapshot copied into local schema 0012. Copied `history_audit.changes_json` has those same fields removed from `before`/`after`, matching migration 0010. Destination-only columns retain migration defaults/nulls, including `club_rotation.human_order` (`{}`), rotation/cycle `classics_first` (0) and `movies.director` (null). Sanitisation otherwise preserves product rows (including roles, avatars, private Builder, deleted events and audit), empties `auth_sessions`/`provider_cooldowns`, replaces authorised emails with unique `@bookclub.invalid` values and clears Google sub/binding/login timestamps. The demo seed marker prevents fresh demo history entering the snapshot.

Before replacement, per-table counts, SQLite integrity/FKs and actual local-emulator catalog, History, Metrics, Watch Order and per-owner Builder reads must pass. Guards confine filesystem operations to local state; API must be stopped for swap. Prior local D1 is retained at `worker/.wrangler/state/v3/d1-before-refresh-<timestamp>`. Rename failure restores it; supervised Worker-start failure attempts previous-state restore/restart. Retained state is private disposable local data, not a production backup. Local edits never sync upstream.

Restore/copy failures report the stage and, for copy operations, the schema/table/operation with allow-listed SQLite error categories; private SQL, row values and raw upstream messages are suppressed. Raw export is removed on completion/handled failure; a crash may leave ignored private temporary files or `worker/.wrangler/dev-refresh.lock`. Stop processes before inspecting/removing stale files/locks; check resolved paths. CLI reports capture time/counts/rotation. `/__dev/refresh` is a local tooling surface described in [CONTRACTS](CONTRACTS.md#development-refresh-boundary).

The production archive tooling can create timestamped SQL exports with SHA-256/count/target/capture proof before guarded mutation; preserve the original pristine export and independent copy. Export integrity is not a tested restore. No scheduled production backup or general automatic production rollback is implemented. Soft-deleted History has audited admin restoration; this is distinct from whole-database restore.

## Data safety and unknowns

Snapshots still contain private product data after auth sanitisation: do not share/commit them, logs, screenshots or private archive artefacts. Never read/print credential-bearing `OWNER_INFO.md` for setup. Ordinary local commands use `--local --env local`; preview uses its isolated config/state. `db:reset` is explicitly destructive local-only; never use it on production. Never seed generic identities to production.

Live schema/rotation and backup availability cannot be certified from source. Verify them only within the authorised operational task; do not reset production to satisfy historical null-sub/avatar/no-session bootstrap assertions.
